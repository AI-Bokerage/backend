Integrating gen-auth-starter

A Spring Boot starter that drops a complete, self-contained auth module — register, login, refresh rotation, logout, sessions, JWKS with runtime key rotation, plus optional email/magic-link, super-admin/impersonation, RabbitMQ events, and TOTP MFA — into any Java project. This is the exact, ordered sequence to embed it in a project that has never seen it before, end to end.

00

What you're embedding

One dependency, one auto-configuration class, its own database tables. Nothing shared back to the source project after you pull the artifact.

Included, always on

  • Register / login / refresh (rotation + replay detection) / logout / logout-all
  • Session lookup, change-password
  • JWKS serving + runtime multi-key rotation (local signing mode)
  • Argon2id hashing, Redis-backed lockout
  • Internal user-provisioning endpoint
  • Cookie or JSON token delivery, toggled by property

Not in this module

Nothing left — everything from the original scope, OAuth login included, is now built and shipped in the starter.

Included, optional (off by default)

  • Email sending (SMTP/SES) + magic-link password reset
  • Super-admin login, bootstrap, impersonation-token issuance
  • RabbitMQ event publishing (login/logout/password-changed/impersonation)
  • TOTP multi-factor auth + backup codes, per-tenant enforcement
  • OAuth / social login — done (Spring Security OAuth2 Client, any OIDC provider)

The optional-feature pattern

  • Every one of these is a single app.*.enabled flag, default false
  • Off means zero cost: no beans registered, no required env vars, no connection attempted
  • See chapter 06 for exact flags, env vars, and config for each

Everything under com.example.authsvc.* ships inside the jar and is discovered automatically via META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports — regardless of your own application's base package. You will not write a @ComponentScan, @EntityScan, or @Import anywhere in your own code. That work is done once, inside the starter, by GenAuthAutoConfiguration.

01

Add the package repository

The starter is a private Maven artifact on GitHub Packages. Your build needs to know where to find it and how to authenticate.

Add the GitHub Packages repository to your build

In the consuming project's root build.gradle, alongside your existing repositories:

build.gradlerepositories {
    mavenCentral()

    maven {
        name = "GitHubPackages"
        url = uri("https://maven.pkg.github.com/YOUR_GITHUB_ORG/Gen_Auth")
        credentials {
            username = project.findProperty("gpr.user") ?: System.getenv("GITHUB_ACTOR")
            password = project.findProperty("gpr.token") ?: System.getenv("GITHUB_TOKEN")
        }
    }

    // Required transitively: spring-security-saml2-service-provider pulls in
    // OpenSAML, which only resolves from Shibboleth's own repository.
    maven {
        url = "https://build.shibboleth.net/nexus/content/repositories/releases/"
    }
}

Authenticate against GitHub Packages

GitHub Packages requires a Personal Access Token with read:packages scope, even for a public-looking read. Put it in your per-user Gradle properties, never in the project itself:

~/.gradle/gradle.propertiesgpr.user=your-github-username
gpr.token=ghp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

CI runners should instead export GITHUB_ACTOR / GITHUB_TOKEN — the block above falls back to those automatically.

Current state of this repo

The publish config's target org, YOUR_GITHUB_ORG, is still a placeholder — nobody has pointed it at a real GitHub org yet, so a real remote publish/consume has not happened. If you're integrating today, skip to chapter 12 and use mavenLocal() instead. Come back to this chapter once the org is filled in and a version is actually published.

02

Declare the dependency

One implementation dependency, plus one you might not expect.

Add the starter to your application module

app/build.gradleplugins {
    id 'java'
    id 'org.springframework.boot' version '4.0.6'
    id 'io.spring.dependency-management' version '1.1.7'
}

dependencies {
    implementation 'com.example:gen-auth-starter:0.0.1-SNAPSHOT'

    // gen-auth-starter is a java-library module: its own Spring Boot
    // dependencies are declared `implementation`, which java-library does
    // NOT expose transitively to a consumer's compile classpath (only `api`
    // dependencies are). Your own @SpringBootApplication class needs this
    // directly on your classpath regardless.
    implementation 'org.springframework.boot:spring-boot-starter'
}
Version alignment

The starter is built and tested against Spring Boot 4.0.6 on Java 21. Import the same BOM your consuming app already uses via io.spring.dependency-management, or apply the org.springframework.boot Gradle plugin as shown above — either keeps transitive versions aligned with what the starter was verified against.

03

Generate the JWT signing keypair

Local signing mode (the default) reads an RSA keypair from your classpath. Generate your own — never reuse a keypair from another deployment.

terminalmkdir -p src/main/resources/keys
openssl genrsa -out src/main/resources/keys/private.pem 2048
openssl rsa -in src/main/resources/keys/private.pem \
    -pubout -out src/main/resources/keys/public.pem
Do not commit these

Add src/main/resources/keys/private.pem and public.pem to your .gitignore before your first commit, not after. A real private key sat briefly in this project's own git history during development for exactly this reason — it was scrubbed via squash-merge before reaching main, but the safer move is to never let it happen at all.

04

Write your application.yaml

The starter ships no root application.yaml of its own — every property below belongs in your consuming project's own config.

src/main/resources/application.yamlspring:
  main:
    allow-bean-definition-overriding: true   # see chapter 11 if you skip this

  datasource:
    url: ${AUTH_DB_URL}
    username: ${AUTH_DB_USERNAME}
    password: ${AUTH_DB_PASSWORD}
    driver-class-name: org.postgresql.Driver

  jpa:
    open-in-view: false
    hibernate:
      ddl-auto: validate     # the starter owns its own schema via Flyway, see ch. 07

  data:
    redis:
      host: localhost
      port: 6379

app:
  cors:
    allowed-origins: [ "http://localhost:3000" ]
    allowed-methods: [ GET, POST, PUT, PATCH, DELETE, OPTIONS ]
    allowed-headers: [ Authorization, Content-Type, Accept, X-Requested-With ]
    allow-credentials: true
    max-age: 3600
  cookie:
    domain: ${COOKIE_DOMAIN:}
    secure: ${COOKIE_SECURE:false}
    http-only: true
    same-site: Strict
    path: /

jwt:
  issuer: ${JWT_ISSUER:https://auth.example.com}
  audience: ${JWT_AUDIENCE:example-api}
  key-id: auth-key-v1
  signing-mode: local
  active-kid: auth-key-v1
  access-token:
    expiration-minutes: 15
  refresh-token:
    expiration-days: 7
  keys:
    - kid: auth-key-v1
      private-key-path: classpath:keys/private.pem
      public-key-path: classpath:keys/public.pem
  key-encryption-secret: ${JWT_KEY_ENCRYPTION_SECRET}

internal-service-secret: ${INTERNAL_SERVICE_SECRET}

auth:
  registration-mode: ${REGISTRATION_MODE:open}     # open | disabled
  token-delivery-mode: ${TOKEN_DELIVERY_MODE:cookie} # cookie | json
  session:
    concurrent-session-limit: 5
  refresh-token:
    rotate-on-refresh: true
    one-time-use: true

Every block above binds to a plain @ConfigurationProperties class the starter registers via @ConfigurationPropertiesScan — JwtProperties, CookieProperties, CorsProperties, AuthBehaviorProperties. None of them are beans you declare; they only exist because they were scanned.

06

Optional features

Four subsystems, each gated by its own app.*.enabled flag, default false. Off means genuinely off — no bean registered, no connection attempted, no env var required. Turn on only what you need.

Email sending + magic-link password reset

app.email.enabled (default false) registers either an SMTP or SES EmailProvider, selected by app.email.provider (smtp default, or ses). app.magic-link.enabled additionally hard-requires app.email.enabled=true — a magic link with no way to deliver it is a broken feature, not a partial one, and the starter fails fast at boot if you enable one without the other.

application.yamlapp:
  email:
    enabled: true
    provider: smtp   # smtp | ses
  magic-link:
    enabled: true

mail:
  provider: smtp

spring:
  mail:
    host: ${MAIL_HOST:localhost}
    port: ${MAIL_PORT:1025}
    username: ${MAIL_USERNAME:}
    password: ${MAIL_PASSWORD:}

auth:
  magic-link:
    frontend-reset-url: https://your-app.example.com/reset-password

SES mode reuses the same AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY variables as KMS signing mode (chapter 05) — blank falls back to the SDK's default credential chain either way. Endpoints: POST /api/v1/auth/magic-link/issue, POST /api/v1/auth/magic-link/verify (full reference in chapter 09).

Super-admin login, bootstrap, and impersonation

app.super-admin.enabled (default false) gates a platform-super-admin account — separate from auth_users by design — plus impersonation-token issuance. It hard-requires both app.email.enabled=true and app.magic-link.enabled=true (the super-admin's password-reset flow reuses the same Redis-backed magic-link store), enforced by a fail-fast @PostConstruct validator, not just documentation.

application.yamlapp:
  super-admin:
    enabled: true

auth:
  super-admin:
    email: ${SUPER_ADMIN_EMAIL}
    password: ${SUPER_ADMIN_PASSWORD}

SUPER_ADMIN_EMAIL/SUPER_ADMIN_PASSWORD seed the bootstrap account on first boot only — change the password immediately after first login. Endpoints: POST /api/v1/auth/super-admin/login, POST /api/v1/auth/super-admin/reset-password/issue, POST /api/v1/auth/super-admin/reset-password/verify, and internally POST /internal/auth/impersonation-token (guarded by the same X-Internal-Secret mechanism as every other internal route — no bespoke auth scheme).

RabbitMQ event publishing

app.messaging.enabled (default false) turns on outbound-only event publishing — login success/failed, logout, password-changed, impersonation-started — onto a single topic exchange, name configurable via app.messaging.exchange (default auth.events). The starter declares only the exchange; it never declares queues or bindings — that topology is entirely yours to own as the consumer.

application.yamlapp:
  messaging:
    enabled: true
    exchange: auth.events

spring:
  rabbitmq:
    host: ${RABBITMQ_HOST:localhost}
    port: ${RABBITMQ_PORT:5672}
    username: ${RABBITMQ_USERNAME:guest}
    password: ${RABBITMQ_PASSWORD:guest}

No HTTP surface — this is fire-and-forget on the existing async executor, and a publish failure (broker unreachable) is caught and logged, never propagated back into the auth request that triggered it.

MFA — TOTP + backup codes

app.mfa.enabled (default false) adds per-user TOTP enrollment (RFC 6238, any standard authenticator app), 10 single-use backup codes, and per-tenant enforcement via an internal endpoint. The TOTP secret is encrypted at rest with its own key — mfa.secret-encryption-key — deliberately separate from jwt.key-encryption-secret so a compromise of one never unlocks the other.

application.yamlapp:
  mfa:
    enabled: true

mfa:
  secret-encryption-key: ${MFA_SECRET_ENCRYPTION_KEY}

MFA_SECRET_ENCRYPTION_KEY follows the same shape as JWT_KEY_ENCRYPTION_SECRET — 32-byte base64, generate with openssl rand -base64 32. When MFA applies to a user, POST /api/v1/auth/login's response shape changes from real tokens to {"mfaRequired":true,"challengeToken":"...","enrollmentRequired":bool} — the client then completes the flow against the MFA-specific endpoints below (full reference in chapter 09):

OAuth / social login

app.oauth.enabled (default false) enables Spring Security OAuth2 Client support for any OIDC provider. The starter ships with a pre-configured example for Google; other providers (GitHub, Microsoft, Apple, or any custom OIDC issuer) follow the same pattern in spring.security.oauth2.client.

application.yamlapp:
  oauth:
    enabled: true

spring:
  security:
    oauth2:
      client:
        registration:
          google:
            client-id: ${OAUTH_GOOGLE_CLIENT_ID}
            client-secret: ${OAUTH_GOOGLE_CLIENT_SECRET}
            scope:
              - openid
              - email
              - profile
        provider:
          google:
            issuer-uri: https://accounts.google.com

Create your OAuth client credentials in your provider's console (e.g. Google Cloud > APIs & Services > Credentials), then set OAUTH_GOOGLE_CLIENT_ID and OAUTH_GOOGLE_CLIENT_SECRET environment variables. The redirect URI is always http://localhost:8080/login/oauth2/code/{provider} (locally) or your production base URL + the same path.

New account flow: visit /oauth2/authorization/google, authenticate with your provider account. If the email is unknown, you land on passwordSetupRequired with a time-boxed setupToken — set a password via POST /api/v1/auth/oauth/complete-signup to finish registration. Returning users skip the password-setup step and log in directly. Existing password-account emails auto-link: if you registered with user@example.com normally, then OAuth-login with a provider account whose email is also user@example.com, you get one merged account and real tokens immediately. Auto-linking additionally requires the provider to assert email_verified: true on the OIDC claim — if the email matches an existing account but the provider has not verified it, the response is 409 {"error": "oauth_email_not_verified"} and the user must log in with their password instead.

MethodPathAuthNotes
GET/oauth2/authorization/googlenoneRedirect to provider login
POST/api/v1/auth/oauth/complete-signupsetupToken (JSON body)Set password for a fresh OAuth account; returns real tokens
GET/login/oauth2/code/googlenoneProvider callback (automatic, user never visits directly)

MFA applies the same way as with password login: if the tenant requires MFA (/internal/auth/tenants/{tenantId}/mfa-required), complete-signup returns {"mfaRequired":true,"challengeToken":"...","enrollmentRequired":true} instead of real tokens, and the client must complete the MFA enrollment or verification flow (chapter 06) before it can exchange the challenge token for real tokens.

07

Database & migrations

There is nothing for you to run here — this is the one chapter that's mostly reassurance.

The starter carries its own Flyway migrations on its classpath and runs them against the same DataSource your app already configured from AUTH_DB_*, tracked in a dedicated history table: flyway_schema_history_auth. This is deliberately not Flyway's default table name, so it can never collide with your own application's migration history — run your own Flyway or Liquibase however you already do, completely independently.

The migration runs via GenAuthFlywayInitializer, an InitializingBean wired to complete before Hibernate's schema validation (ddl-auto: validate) ever runs, via GenAuthJpaDependsOnFlywayConfig. You do not need to declare an ordering dependency yourself — it's built into the auto-configuration.

A minimal smoke test before you build anything on top.

# expect: {"status":"UP"}

curl -i -X POST http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"dev@example.com","password":"correct horse battery staple"}'
# expect: 201

curl -i -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"dev@example.com","password":"correct horse battery staple"}'
# expect: 200, Set-Cookie headers (cookie delivery mode is the default)

If registration or login 401s immediately, jump to chapter 10 — it's almost always a security-filter-chain conflict, not a config typo.

10

If you have your own SecurityFilterChain

The single most likely integration snag. Read this before you file a bug.

The starter registers its own SecurityFilterChain bean (inside SecurityConfig) and forces itself to be configured before Spring Boot's own default via @AutoConfigureBefore(ServletWebSecurityAutoConfiguration.class) on GenAuthAutoConfiguration. Two consequences:

You don't need your own SecurityFilterChain just to use the starter

Boot it as-is and the starter's filter chain handles everything under /api/v1/auth/**, /internal/**, and /.well-known/jwks.json.

If your own app defines a SecurityFilterChain bean too

Spring only keeps one SecurityFilterChain per matcher scope. Two unscoped chains in the same context is a startup error, not a silent merge. Scope yours with a narrower securityMatcher(...), or give it explicit @Order relative to the starter's, so your routes and the starter's auth routes are unambiguous about which chain owns which path.

Field notes & gotchas

Three things that cost real debugging time during this project's own verification passes — all three needed a live boot to surface, not a unit test.

allow-bean-definition-overriding

If your own app also defines beans the starter's @ComponentScan discovers (unlikely, since everything lives under com.example.authsvc, but possible for shared library beans), set spring.main.allow-bean-definition-overriding: true. Without it you'll see Spring's normal duplicate-bean-definition error, which is at least honest about what's wrong.

JVM timezone

If your JVM's default timezone resolves to a legacy IANA alias your Postgres image's tzdata doesn't recognize (e.g. Asia/Calcutta instead of Asia/Kolkata), every DB connection fails with invalid value for parameter "TimeZone". Fix: JAVA_TOOL_OPTIONS=-Duser.timezone=UTC. It must be this exact env var — a -D flag passed to gradlew on the command line does not propagate into bootRun's forked JVM.

Local Postgres/Redis port collisions

If your machine already runs a native Postgres or Redis on the default ports, a container published on 5432/6379 can silently lose to the native install when the JVM connects from the host side — you'll get a confusing "password authentication failed" instead of a clean connection-refused. Publish your dev containers on non-default host ports (e.g. 5433/6380) and point AUTH_DB_URL/spring.data.redis.port at those instead.

Upgrading an existing install to this version

JWT_KEY_ENCRYPTION_SECRET is checked unconditionally at boot on this version, even for installs that will only ever use YAML-sourced keys or kms signing mode and never call the rotation endpoints. Set it before you deploy, not after the first crash loop.
